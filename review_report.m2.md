# Deep Review: `feat/task-dag-foundations`

**Scope:** 47 commits, 151 files, +39610 / −10246 vs `main`. Adds a task DAG / workflow execution layer (dependencies, contracts, gates, fan-out, loops, branching) and replaces the OpenAI device-OAuth + GitHub Copilot auth flows with the pre-existing `crate::auth` (Anthropic OAuth) module.

## Verdict

**Do not merge until P1 fixes land.** Two P1 findings — an HTTP-gate SSRF read primitive and a fan-out expansion TOCTOU race that duplicates branches — each represent a class of bug this branch's own design notes say it was written to prevent. The core scheduler state machine, loop double-emit guard, auth cutover, and migration safety are all sound; the gaps are concentrated in the HTTP gate and the fan-out path.

## Residual Risk

- **Runtime behavior under load:** The loop boundary guard is race-safe under SQLite's `BEGIN IMMEDIATE` serialization, but the fan-out path (#2) is not — and fan-out is the feature most likely to run concurrently (sweep + completion path). The duplicate-branch outcome doubles downstream model spend, which is the exact "unbounded spend" risk the loop `max_iterations` ceiling exists to prevent.
- **SSRF exploitability:** The HTTP gate is reachable by any API-token holder, not just a trusted operator. If the instance runs on a cloud VM, the `169.254.169.254` metadata endpoint returns IAM credentials without authentication. The `last_detail` exfiltration makes this a read primitive, not just a blind request.
- **External systems:** The gate HTTP evaluator makes outbound requests on a timer with nobody watching; a malformed or malicious gate URL persists and is polled every 15s minimum. The `GATE_ERROR_LIMIT=5` backoff mitigates unreachable endpoints but not SSRF targets that respond 200.
- **SQLite concurrency:** All transactional guards rely on `BEGIN IMMEDIATE` serialization. This is correct for SQLite but means concurrent writes block. Under high fan-out + loop + completion contention, this could manifest as latency, not correctness (excepting #2).

## Open Questions

1. **SSRF scope (#1):** Is the HTTP gate intended to be authorable by all API-token holders, or only by trusted operators in a controlled network? If the former, the private-IP filter is mandatory; if the latter, documenting the trust boundary may suffice. The recommendation assumes the stricter case.
2. **Fan-out race urgency (#2):** Does the sweep's `expand_fan_outs` and the completion path's `expand_fan_outs_for` actually run concurrently in production, or is there a higher-level lock that serializes them? If serialized, #2 downgrades to P2; if concurrent (as the code structure suggests), it stays P1.
3. **`evaluate_http` 5xx (#3):** Should a 4xx also map to `Erroring` or stay `Pending`? The current design treats 4xx as a definitive "no" (Pending/Failed), which is defensible for a 404 but questionable for a 429. The recommendation focuses on the unambiguous 5xx case.
